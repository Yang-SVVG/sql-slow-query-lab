# 三个案例：症状 → 诊断 → 处理

每个案例都按「报表现象 → 我先看什么 → 计划怎么变 → 数字」写，方便对上自己遇到的场景。

## 案例 1：只查三天，还要 17 毫秒

**现象**：运营看板的「昨日实时」查询，日期范围只有 1 天，但每天第一次打开都卡。

**诊断**：`EXPLAIN QUERY PLAN` 显示 `SCAN f_orders`，30 万行全扫。过滤列 `paid_at` 上没有索引。

**处理**：建复合索引 `(paid_at, status)`。顺序不能反 —— `status` 只有 3 个取值、88% 都是 `paid`，放前面等于没走索引。

**数字**：13.3 ms → 1.1 ms（×12）。倍数不算夸张，但这 16 倍是零成本的，改一行 DDL。

## 案例 2：加了 WHERE 还是 3.6 秒

**现象**：订单明细汇总，SQL 明明带了日期和区域过滤，仍要 4 秒。

**诊断**：计划里 `CORRELATED SCALAR SUBQUERY 1` 内部是 `SCAN i`。外表命中 216 行，每行扫 61 万行明细 → 约 1.3 亿次行访问。

**处理**：给 `f_order_items(order_id)` 建索引，**SQL 一个字没改**。

**数字**：3.64 s → 1.5 ms（×2386）。最典型的「索引改命」场景：不值得先改写 SQL，先看计划。

## 案例 3：看板每天重算半年数据

**现象**：经营分析看板（月 × 区域，48 行结果）每次打开都要 101 ms，并发一上来就排队。

**诊断**：每次都在扫订单 + 关联客户 + 分组。结果集只有 48 行，但源数据 30 万行。

**处理**：预聚合表 `dws_month_region` + 唯一索引 `(stat_month, region)`，每天调度刷新一次。

**数字**：101.3 ms → 125 µs（×810），代价是构建 220 ms（一天一次）。

**边界**：预聚合只能回答「维度固定」的问题。一旦要按新维度（渠道 × 品类）看，就得再建一张表 —— 空间换时间，不是免费的。

## 反例：改写不一定更快

为了让案例 2 更「漂亮」，我试过把相关子查询改写成：

```sql
SELECT o.order_id, SUM(i.qty * i.unit_price) AS item_amount
FROM f_orders o
JOIN f_customers c ON c.customer_id = o.customer_id
JOIN f_order_items i ON i.order_id = o.order_id
WHERE ... GROUP BY o.order_id;
```

计划变成了「先扫 61 万行明细，再回查订单」，实测 **43.3 ms**；加 `CROSS JOIN` 强制连接顺序到 **56 ms** —— 都比带索引的相关子查询（2.2 ms）慢一个数量级。

结论：**同一语义有多种写法，执行计划才决定谁快。** 这个反例留在文档里，不进基准表 —— 基准表只收「我最终会推荐给别人的写法」。
